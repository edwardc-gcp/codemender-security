# CodeMender Configuration Reference (`.codemender/config.yaml`)

This document reflects the exact, ground-truth configuration schema generated by `cm init` in **CodeMender 0.17.0 through 0.21.0** (the template hasn't changed since 0.17.0, observed; notes mark where 0.16.0 differs), along with the **Surgical Tuning Playbook** for troubleshooting scan coverage and performance.

---

## 1. Ground-Truth `config.yaml` Schema (`cm init` 0.17.0 through 0.21.0)

```yaml
# CodeMender CLI configuration.
# The server endpoint is baked in at build time (see build profiles).
# Override it here only if you need a different endpoint.

server: {}

# Customer-supplied team identifier sent as the X-CodeMender-Team-Id
# telemetry header. Overridden by --team-id flag or $CM_TEAM_ID env var.
# Max 63 chars, must match [A-Za-z0-9._-]. Omit to skip the header.
# team_id: "acme-security"

scan:
  extensions:
    include: [".py", ".java", ".go", ".js", ".jsx", ".mjs", ".cjs", ".ts", ".tsx", ".c", ".cc", ".cpp", ".cxx", ".h", ".hh", ".hpp", ".hxx", ".inl", ".ipp", ".cs", ".rs", ".kt", ".kts", ".rb", ".php", ".sol", ".tf", ".hcl"]
    exclude: [".min.js", ".generated.go", ".pb.go"]
  # A leading "/" matches only that directory at the scan root.
  exclude_dirs: ["node_modules", "vendor", "dist", "/target", "/obj", "/build", ".gradle"]
  max_file_size_kb: 2048
  incremental: true

# Restrict agent file access to these directories (all commands).
# When empty, the scan target directory is used as the boundary.
# project_paths:
#   - "/path/to/project"
#   - "/path/to/shared-lib"

output:
  format: table   # "table", "json", "sarif"
  # plain: false  # Disable emojis, Unicode glyphs, and terminal colors (or set CM_PLAIN=true)

tools:
  confirm_commands: true   # Prompt Y/N before running shell commands (default: true)
  confirm_writes: true     # Prompt Y/N before writing/modifying files (default: true)
  # cleanup_candidate_branches: true # Auto-delete temporary candidate branches on completion (default: true)
  # Use --yes flag on find/fix/session resume to skip all confirmations

vcs:
  type: ""               # VCS type: "git", "mercurial", "custom", or "" (auto-detect)
  commands:
    reset: ""            # Shell command to reset codebase (auto-populated for known VCS)
    diff: ""             # Shell command to show changes (auto-populated for known VCS)
    status: ""           # Shell command to list modified files (auto-populated for known VCS)
    stage: ""            # Shell command to stage changes (auto-populated for known VCS)
  # Known VCS types (git, mercurial) auto-populate commands.
  # For custom VCS, you MUST set the commands above.
  # Examples:
  #   type: git           # uses: git checkout HEAD -- . && git clean -fd
  #   type: mercurial     # uses: hg revert --all --no-backup && hg purge
  #   type: custom
  #   commands:
  #     reset: "./scripts/reset.sh"
  #     diff: "diff -rq baseline/ current/"
  #     stage: "git add -A"

build:
  command: ""              # Shell command to build/verify changes from the agent
  # Examples:
  #   Make:       "make build && make test"
  #   Go:         "go build ./... && go test ./..."
  #   Custom:     "./scripts/verify.sh"
```

The only difference from the 0.16.0 template is the commented `plain` line under `output`.

## 1b. Additional Official Public-Doc Blocks (`sandbox`, `security`, `execution`)

While `cm init` generates the concise template in Section 1, the official CodeMender documentation also defines optional blocks that can be added to `.codemender/config.yaml`:

```yaml
sandbox:
  enabled: true            # false runs agent tools directly on the host: explicit user consent required
  mounts:
    target_dir: "."        # directory mounted as the workspace (relative to the workspace root)
  network:
    # "permissive-closed" (default: blocks all outbound connections during tool runs)
    # "permissive-open"   (full outbound network access for builds/tests while keeping filesystem sandboxing)
    profile: "permissive-closed"

security:
  # Additional host paths mounted read-only inside the sandbox (0.17.0 always protects
  # .git/hooks, .git/config, .hg/hgrc, and .codemender, and excludes common credential directories)
  protected_files:
    - "~/.ssh/*"
    - "~/.aws/*"
    - "~/.config/gcloud/*"

execution:
  interactive_mode: true   # false turns off command and file-write prompts for every run (0.17.0 docs)
```

> **Key names**: Older CodeMender docs used `human_confirmation` / `require_confirmation`; the current docs and the `cm init` template use `tools.confirm_commands` / `tools.confirm_writes` (and `execution.interactive_mode` for both) and `scan.exclude_dirs`. Always use the template's key names (Section 2). `cm` doesn't warn about unknown or misspelled keys (observed with 0.16.0 and 0.17.0: `cm init --verify` still reports "Config loaded successfully"), so after every edit run `cm_config_check.sh` (undocumented keys, invalid values) plus `cm_exec.sh init --verify` (YAML syntax, `team_id`).

## 1c. Command Policy (`command_policy.yaml`, 0.17.0)

Besides `config.yaml`, cm 0.17.0 reads a command denylist for the agent's shell commands from `~/.codemender/command_policy.yaml` (global) and `<project>/.codemender/command_policy.yaml` (project); when both exist, the rules are merged. With `cm_exec.sh`, both are the repository's `.codemender/`. On first run (also through `cm init`), cm creates a commented-out template:

```yaml
# block:
#   - curl
#   - wget
#   - ssh
#   - sudo
#   - rm
# block_patterns:
#   - '\bgit\s+(push|commit|rebase|reset\s+--hard|clean)\b'
```

* `block`: binary names to block across pipelines, subshells, and command substitutions.
* `block_patterns`: regular expressions matched against each command segment.
* Nothing is blocked out of the box, because the OS sandbox already isolates commands. Add rules to tighten a repository; never remove rules or pass `--allow-all-commands` (which skips the policy for one run) without the user's consent.

## 2. Complete Key Reference (cm 0.17.0 through 0.21.0)

`cm` reads `$CM_HOME/config.yaml` (`~/.codemender/config.yaml` by default; `.codemender/config.yaml` in the repository with `cm_exec.sh`). Every key below comes from the `cm init` template, the public config docs, or the release notes; don't add keys that aren't listed.

| Key | Type | Default | Effect and when to change it |
| :--- | :--- | :--- | :--- |
| `server` | map | `{}` | Server settings. The template notes that the endpoint is built in and can be overridden here only if you need a different one: leave it `{}`. |
| `team_id` | string | none | Telemetry team ID (`X-CodeMender-Team-Id`); at most 63 characters from `[A-Za-z0-9._-]`. Overridden by `--team-id` and `CM_TEAM_ID`. An invalid value fails `cm init --verify` (observed) and `cm health` (exit `20`). |
| `scan.extensions.include` | list | 28 suffixes (Section 1) | Extensions that deep and quick scans read. Add only the languages the repository uses (Section 4). |
| `scan.extensions.exclude` | list | `.min.js`, `.generated.go`, `.pb.go` | Suffixes to skip, such as generated or minified files. |
| `scan.exclude_dirs` | list | `node_modules`, `vendor`, `dist`, `/target`, `/obj`, `/build`, `.gradle` | Directories to skip. A name matches at any depth; a leading `/` matches only at the scan root. |
| `scan.include_hidden` | bool | `false` | Scans dot-prefixed directories and files, like `--include-hidden` (release notes 0.12.0; not shown in the template). |
| `scan.max_file_size_kb` | int | `2048` | Larger files are skipped; raise it for big generated or monolithic files. |
| `scan.incremental` | bool | `true` | Template default; the docs don't describe it, so leave it as is. It isn't diff mode: use `--diff` to scan only your git changes. |
| `project_paths` | list | `[]` | Directories the agent may read and write during tool runs, for example a shared library outside the project. When empty, the 0.17.0 docs restrict the agent to the enclosing project root (or the scan target directory). The session artifacts directory is always writable; the host `/tmp` stays blocked even if listed; writes to `.git`, `.hg`, and `.codemender` are always blocked. `--allow-all-paths` lifts the boundary for one run (user consent required). |
| `output.format` | string | `table` | Default report format: `table`, `json`, or `sarif`. |
| `output.plain` | bool | `false` | 0.17.0: ASCII-only CLI output and `table`, `md`, and `html` reports, for CI logs and screen readers (same as `--plain` or `CM_PLAIN=true`). `json` and `sarif` don't change. |
| `tools.confirm_commands` | bool | `true` | Asks before each shell command. Keep `true` and pass `-y` per run instead. |
| `tools.confirm_writes` | bool | `true` | Asks before each file write. Keep `true` and pass `-y` per run instead. |
| `tools.cleanup_candidate_branches` | bool | `true` | Deletes the temporary candidate branches after a run. |
| `execution.interactive_mode` | bool | `true` | 0.17.0 docs: `false` turns off both command and file-write prompts for every run (it wins over `tools.confirm_*`; `-y` wins over it). Keep `true` and pass `-y` per run instead. |
| `vcs.type` | string | `""` (auto-detect) | `git`, `mercurial`, `custom`, or `none` (runs without VCS support, with a warning). |
| `vcs.commands.reset` / `diff` / `status` / `stage` | string | auto for git and mercurial | Required for `type: custom`. For git, reset is `git checkout HEAD -- . && git clean -fd`. |
| `build.command` | string | `""` | Build and test command that `cm fix` runs (inside the sandbox, from the finding's directory) to validate a patch. Anchor it to the repository root; `"true"` skips the check. Since 0.21.0, `cm build` runs it in the same sandbox, so `cm_exec.sh build --force` checks it without model tokens. |
| `sandbox.enabled` | bool | `true` | `false` runs agent tools directly on the host, like `--sandbox=false` (since 0.17.0 the path boundary and command policy still apply): **explicit user consent required**. |
| `sandbox.mounts.target_dir` | string | `.` | Directory mounted as the active workspace, relative to the workspace root. |
| `sandbox.network.profile` | string | `permissive-closed` | `permissive-closed` blocks all outbound connections; `permissive-open` allows them all (no per-domain allowlists). |
| `security.protected_files` | list | `[]` | Additional host paths mounted read-only inside the sandbox; supports `~` and `*`. Since 0.17.0, `.git/hooks`, `.git/config`, `.hg/hgrc`, and `.codemender` are always read-only, even when this list is empty. |
| `model` | string | `gemini-3.8-flash` | Listed in the config docs as the default model. The plugin passes `--model` on the command line instead (documented for `find`, `verify`, and `fix`), so every run states its model. |

## 3. Key Parameters Breakdown

### `scan`
* `scan.extensions.include`: Whitelist of file extensions for deep and quick scans. Since `v0.16.0`, defaults to 28 suffixes (`[".py", ".java", ".go", ".js", ".jsx", ".mjs", ".cjs", ".ts", ".tsx", ".c", ".cc", ".cpp", ".cxx", ".h", ".hh", ".hpp", ".hxx", ".inl", ".ipp", ".cs", ".rs", ".kt", ".kts", ".rb", ".php", ".sol", ".tf", ".hcl"]`), covering backend, frontend React/TypeScript, systems languages (including C++ headers and inline sources), Solidity, and Terraform IaC out of the box. Diff scans (`--diff`) ignore this list: every changed tracked file is scanned.
* `scan.extensions.exclude`: Suffixes skipped during scanning (`[".min.js", ".generated.go", ".pb.go"]`).
* `scan.exclude_dirs`: Directories skipped during scanning (defaults to `["node_modules", "vendor", "dist", "/target", "/obj", "/build", ".gradle"]`). A leading `/` matches only that directory at the scan root, so nested `target/`, `obj/`, and `build/` directories (for example `services/api/build/`) are scanned. `bin` is no longer excluded by default.
* `scan.include_hidden`: Optional boolean (`true` / `false`) to include dot-prefixed directories (e.g., `.github/`, `.config/`) and files during discovery (can also be enabled per run via `cm find --include-hidden`). The template doesn't show this key.
* `scan.max_file_size_kb`: File size threshold (default `2048` KB / 2 MiB) to skip large binary/data assets.
* `scan.incremental`: **(Default: `true`)** Template default that the docs don't describe further, so leave it as is. It is not diff mode: to scan only your git changes, use `cm find --diff` (or `cm_diff_scan.sh`).

### `tools` and `execution` (Traceability Rule)
* `tools.confirm_commands` & `tools.confirm_writes`: Default to `true`; `execution.interactive_mode: false` turns both off.
* **Best Practice**: **Keep all three at their defaults in `.codemender/config.yaml`.** Do not mutate `config.yaml` to disable confirmations; instead, explicitly pass `--bypass-warning -y` on the CLI command line so non-interactive execution remains visible and auditable in shell logs. If no one can answer a prompt and none of these settings applies, cm doesn't run the command or write the file (0.17.0 docs).

### `vcs`
* `vcs.type`: VCS provider. Defaults to `""` for automatic detection (`git` or `mercurial`).
* **VCS Safety Note**: Notice that `type: git` uses `git checkout HEAD -- . && git clean -fd` for resets!
  1. Always register `.codemender/`, `.cm_project`, and `.exploit/` in `.git/info/exclude` so `git clean -fd` never deletes `.codemender/state.db` mid-session.
  2. `cm fix` runs this reset in its workspace unless `--no-reset` is passed (cm 0.17.0; 0.16.0 has no such flag). `cm_remediate_loop.sh` passes `--no-reset` on 0.17.0 and later and, on every version, commits uncommitted work first in a `wip(cm)` checkpoint commit and restores the working tree afterwards. Don't rely on `git stash`: it hides the very code under review, and it fails while intent-to-add entries (`git add -N`) exist.

### `build`
* `build.command`: Verification command executed by `cm fix` inside the sandbox (`exebox`). `cm fix` runs it from the finding's directory (for example `app/`), not from the repository root, so anchor it to the root: `cd "$(git rev-parse --show-toplevel)" && python3 -m pytest -q`.
* `cm build --force` also runs `build.command`. Since 0.21.0 it does so in the same sandbox as the validation in `cm fix` (release notes; observed), so a pass shows, without model tokens, that `cm fix` can validate patches: `cm_remediate_loop.sh` runs it once before the first fix and stops when it fails. Up to 0.20.0 it ran outside the sandbox (observed with cm 0.16.0 on Linux), so a pass proved less.
* **Tiered Build & Sandbox Resolution**:
  1. Pre-install dependencies on the host and probe the build binary dynamically (`command -v pytest`, `command -v python3`, `command -v node`).
  2. If `build.command` or `cm verify` fails solely because the sandbox blocks network/socket connections (`permissive-closed`), set `sandbox.network.profile: "permissive-open"` in `.codemender/config.yaml` (keeping filesystem isolation active).
  3. If no test suite exists (`npm test` returns 1), or the sandbox blocks host toolchain execution paths (`~/.nvm`, `/opt/homebrew`, `~/.pyenv`; 0.21.0 mounts host toolchains read-only, release notes), or a build needs a credential that cm 0.17.0 hides in the sandbox (credential directories, `*_TOKEN` / `*_KEY` style variables), set `build.command: "true"` in `.codemender/config.yaml` and enforce the real build check via `OUTER_BUILD_CMD` in the outer shell before `git commit`.
  4. If tests fail only inside the sandbox because they write to `/tmp`, make them use `TMPDIR` instead: the host `/tmp` is always blocked in the sandbox, and `TMPDIR` points into the session's artifacts directory.
  5. Since 0.21.0, package and compiler caches start empty inside the sandbox and there's no network, so dependencies must already be in the project: `node_modules/` works (observed with OWASP Juice Shop), while Go modules must be vendored (`go mod vendor`) because the sandbox sets `GOPROXY=off` (observed). Check with `cm_exec.sh build --force` before running `cm fix`.

## 4. Surgical Tuning Playbook (Troubleshooting Coverage vs. Performance)

> **Golden Rule**: Never blindly add every possible extension to `scan.extensions.include` upfront—every extra extension increases file count, scan latency, and token consumption. Only apply surgical adjustments to `.codemender/config.yaml` based on the specific project stack or observed symptom:

| Observed Symptom / Scenario | Root Cause in `config.yaml` | Surgical `config.yaml` Adjustment |
| :--- | :--- | :--- |
| **Vue / Svelte / Swift project files are skipped** | `.vue`, `.svelte`, `.swift` are not in default `scan.extensions.include` | Append **only** the specific suffixes present in the repo (e.g., add `".vue"`, `".svelte"`, or `".swift"` to `scan.extensions.include`) |
| **User asks to audit Kubernetes YAML, CI/CD workflows (`.github/workflows`), or shell scripts** | `.yaml`, `.yml`, `.sh` and dot-prefixed directories (`.github`) are excluded from default discovery | Surgically append `".yaml", ".yml", ".sh"` to `scan.extensions.include` and pass `--include-hidden` (or set `scan.include_hidden: true`) |
| **Scan is unusually slow or consumes excessive tokens on Python / Next.js / coverage-heavy repos** | Virtual environments (`.venv`, `venv`) or framework cache folders (`.next`, `coverage`, `migrations`) are not in default `scan.exclude_dirs` | Append existing virtualenv/cache folders in the workspace to `scan.exclude_dirs`: e.g. `[".venv", "venv", "__pycache__", ".next", "coverage", "migrations", "docs"]` |
| **Deep scan of a monorepo or multi-module build reads build output in nested `build/`, `target/`, `obj/`, or `bin/` directories** | Since `v0.16.0`, `"/target"`, `"/obj"`, and `"/build"` match only at the scan root, and `bin` is no longer excluded | Drop the leading `/` (e.g., `"build"`, `"target"`) when no source code lives in directories with that name, and add `"bin"` only when it holds build output (Go, .NET) |
| **Massive generated or monolithic controller file (>2 MiB) is skipped** | File size exceeds `scan.max_file_size_kb: 2048` | Check file size (`ls -lh <file>`); if >2048 KB, raise `scan.max_file_size_kb` (e.g., to `4096`) for the audit |
| **False positive in a monorepo sub-package because shared sanitizer in `../shared` wasn't read** | `project_paths` defaults to `[]` (the project root or scan target as the least-privilege boundary) | Add the shared package directory to `project_paths: ["/abs/path/to/app", "/abs/path/to/shared"]` |
| **Subdirectory scan (`cm find ./src`) causes `cm verify` / `cm fix` to miss root `Cargo.toml` / `package.json` or creates a nested `<subdir>/.git`** (observed with 0.16.0) | When `project_paths` is empty (`[]`, default for monorepo isolation), `cm __worker` locks `--workspace` and `--allowed-roots` to `./src` and runs `git init` inside `./src` if `.git` is absent. The 0.17.0 docs describe the empty default as the enclosing project root instead | **Keep `project_paths` empty on Turn 1.** If a subdirectory scan in a single-repo project triggers root-file access errors or creates `<subdir>/.git`, reactively set `project_paths: ["/abs/path/to/project_root"]` and remove `<subdir>/.git` & `<subdir>/.gitignore` |
| **`cm verify` or `cm fix` stalls >60s (15+ steps in `.codemender/logs/`) running `which mono` or `find / -name cargo`** | Cloud agent invokes `run_command` to locate compilers blocked by the sandbox (`/opt/homebrew`, `~/.cargo`, `~/.nvm`) | **Keep native `-c` on Turn 1** (preserving in-loop compiler self-correction). Only if `.codemender/logs/` shows compiler-search loops, re-run with `-c "<guidance>. IMPORTANT: Do NOT call run_command in sandbox; apply fix via search_and_replace and rely on outer build gate"` + `--no-cache --bypass-warning -y` |
| **`cm fix` validation fails with "No such file or directory" although `build.command` works from the repository root** | `cm fix` runs `build.command` from the finding's directory (e.g., `app/`), so relative paths break | Anchor the command to the root: `cd "$(git rev-parse --show-toplevel)" && <command>`, or set `build.command: "true"` and rely on the outer build gate (`OUTER_BUILD_CMD`) |
| **An agent shell command fails with a command policy block (0.17.0)** | A rule in `command_policy.yaml` (`block` or `block_patterns`) matches the command | Leave the policy in place and adjust the guidance (`-c`) so the agent avoids that command; only the user may relax the rule or approve `--allow-all-commands` for one run |
